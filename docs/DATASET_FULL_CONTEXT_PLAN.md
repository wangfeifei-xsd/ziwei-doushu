# 命理档案完整上下文修改方案

日期：2026-11-09。状态：业务代码已实施；验证结果与尚未进行的人工评估见文末。

目标：每次命理询问向模型提供匹配生辰的完整档案，优先保证资料完整、事实一致和解释充分；不以节约 token 作为首要目标，不新增由程序判断段落相关性的筛选、评分、重排或摘要。

## 1. 确定后的行为

普通命盘和学习示例：按当前命盘的出生键精确匹配一条记录，将该记录全部 13 个专题的原文注入本次模型请求。

合盘：分别匹配甲、乙两人的出生键，完整注入双方各自的 13 个专题，并保留人物归属。双方同生辰时仍分别标明人物，避免关联关系丢失。

用户问题、选中的主题、宫位、四化、运限及完整会话历史共同作为分析上下文。问题或界面选择改变时，同一出生键的档案正文保持一致，由模型结合完整资料处理本次问题。

全文范围是命中的个人档案：单盘一条记录，合盘两条记录。模型同时接收当前结构化命盘、现有古籍参考和完整会话历史。古籍参考有独立的检索实现；本方案的全文改造对象是压缩档案，避免把档案裁剪与古籍检索混成一项变更。

## 2. 改造前已核对的依据

- 当前档案最多取 3 个候选专题、6 段正文；单盘预算 3600 字符，合盘每方 1800 字符。
- 段落还受 35–1400 字符区间、关键词过滤和跨专题去重影响。
- 实测出生键 `1990-02-06-11-male` 的 13 专题正文共 28776 字符。询问迁移、事业和收入时，当前仅注入 534 字符，全部来自事业专题。
- 原生端对最终模型请求设有 262144 字节限制。按全文方案临时组装的单盘请求为 105736 字节，双盘请求为 217709 字节；双盘在现有限制下只剩约 44 KB 的额外空间。这里是两份样本的 UTF-8 请求大小，未调用模型，不代表所有记录的最大值，也不等于 token 数。
- 共享请求构造器和原生 Rust 转发器均写死 4096 输出 token；提示词还要求回答约 600–1000 字。

## 3. 关闭档案内容限制

取消下列规则在档案注入过程中的作用：

1. 最多 3 个候选专题。
2. 最多 6 段正文。
3. 单盘 3600、合盘每方 1800 字符预算。
4. 段落必须介于 35–1400 字符的要求。
5. 根据问题关键词、主题、宫位、星名对档案排序并决定取舍。
6. 因段落重复而删除原文。
7. 根据“年份、大限、旺、陷”等关键词直接删除整段。

档案正文直接使用原始记录的 `c[topic]`，按固定的 13 专题顺序组织。保留标题、换行、段落、条件、例外说明和引文，不重新概括、改写或截断。正文的完整性可通过逐专题字符串比较验证。

旧版时间、亮度、流派和引文来源通过资料元数据及提示词说明；标记不参与删文。保留主体数据与内嵌引文的来源和许可信息。

## 4. 上下文结构与解释口径

为全文资料增加明确的类型，按人物记录组织：

- 人物：当前盘、甲方或乙方。
- 出生键、读取状态、数据版本、生成日期、来源链接和源引擎版本。
- `topics`：13 个专题，每项包含专题标识、标题及原始 `text`。
- 完整性信息：期望专题数、实际专题数、原始正文字符数、注入正文字符数及是否完整。

使用专题级正文，保留源字符串的原始顺序。引用定位改为出生键、专题、版本；需要定位段落时可附加索引，正文仍保留原样。同步更新系统提示词和引用规则，避免模型继续使用旧结构中的段落字段。

当前排盘引擎提供的十二宫、星曜、四化、所选运限作为本次命盘事实。档案明确标为 2026-10-15 生成的旧版本解释文本。要求模型核对条件，遇到冲突说明来源与差异，不能将档案中的旧年份或“当前大限”直接套用于本次问题，也不能把档案中的生成论述当作已发生的个人经历。

## 5. 单次请求、历史与回答容量

### 请求传输

将 Web 与原生端的 256 KiB 请求限制提升为统一、可配置的 16 MiB 资源保护上限，并分别检查浏览器入站请求及注入全文后的最终模型请求。此值用于异常请求保护，不用于挑选或裁剪资料；超过时明确报错并保留原文。

移除会阻碍完整历史传递的单条 12000 字符限制，以及学习输入和合盘问题的 4000 字符业务限制。保留消息角色、字段类型和非空内容校验，按整包字节数统一处理容量问题。

输入保留完整命盘、命中档案和现有会话历史。不得为使请求成功而自动减少专题、裁剪历史、生成摘要或换成较短资料重试。

### 输出与耗时

移除提示词中固定“600–1000 字”的要求，改为依据问题复杂度和用户要求提供充分说明。

移除共享层及 Rust 层强制设置 4096 输出 token 的行为。模型设置增加可选的输出 token 配置；填写时两端按该值请求，未填写时不强制传入该参数。服务商的默认输出额度和实际模型上限仍然生效，未填写不代表无限输出；需要较长回答时可设置模型支持的较高额度。

正常解读的整体超时改为可配置，首版默认 10 分钟；保留用户主动停止、页面离开取消及连接失败处理。模型连接测试继续使用独立的短超时。

### 模型实际容量

模型上下文窗口和服务商请求限制不能由客户端取消。服务商报告上下文超限、输出额度不兼容或请求体过大时，明确区分错误原因，保留本次问题和完整资料，支持调整模型配置后重试。不得把超限伪装成普通网络故障，也不得自动删文换取请求成功。

## 6. 资料缺失与可核对状态

完整记录加载成功后，界面可显示“已加载 13/13 个专题”；合盘分别显示双方状态。显示范围与正文完整性，不展示内部评分或算法解释。

超出覆盖年份、未命中、读取超时或文件损坏时，明确显示本次档案未注入及原因。继续使用当前命盘和古籍的降级回答必须标明实际资料范围。发现缺少专题或正文不完整时不得显示“完整档案已加载”。

核对信息只记录数量、长度、版本和状态；不把完整命盘或聊天正文写入常规日志。

## 7. 主要修改位置

- `packages/domain/src/ziwei/dataset.ts`：建立全文资料类型和转换函数，以原始 13 专题替代预算选段，关闭档案正文的过滤、排序与删除链路。
- `packages/features/src/ai/dataset.ts`：单盘、学习、合盘统一注入全文，更新读取状态、完整性和来源信息。
- `packages/features/src/ai/prompts.ts`：更新全文解释与引用规则，移除固定回答字数和消息长度业务限制。
- `packages/features/src/ai/client.ts`：移除写死的输出 token 值，处理可选配置及明确的未完成状态。
- `packages/domain/src/ai/config.ts`、`packages/runtime/src/services.tsx`、模型设置及持久化代码：贯通输出额度和超时配置，兼容已有配置。
- `apps/web/lib/ai/server.ts`、`apps/native/src-tauri/src/ai.rs`：统一大请求处理、配置透传、容量错误和取消行为，修复原生端覆盖输出额度的问题。
- 普通命盘、学习及合盘的提问组件：同步输入长度、资料加载状态和错误反馈。
- `scripts/regression/dataset.test.ts`、AI/原生流式回归及对应端到端测试：从“未超过预算”改为验证全文完整及传输一致。
- `docs/ai-context.md`、`docs/dataset-v4-usage-analysis.md`：同步实际行为及容量边界。

## 8. 验收标准

1. **正文完整**：真实样本全部 13 专题的注入正文与压缩记录中的原始正文逐项相等，包括标题、短段、长段、重复内容及原始换行。
2. **问题不改变档案正文**：同一命盘分别询问事业、迁移、财运和综合问题，注入档案正文保持一致；变化发生在问题和分析选择中。
3. **人物不混淆**：合盘双方各有完整 13 专题，出生键及人物归属正确；学习例盘按其实际生辰读取。
4. **跨端一致**：Web 和原生端在 Chat Completions、Responses 两种模式下均完整传输正文；原生转发不会额外裁剪或覆盖配置。
5. **长请求可用**：使用超过旧 256 KiB 门槛的真实资料组合及较长历史，通过本地模拟服务核对最终请求；超过资源上限时明确报错且不发送残缺资料。
6. **输出配置有效**：未配置时不注入写死的 4096；配置较高额度后，最终请求保留该值。输出达到服务商上限、中断或缺失完成信号时明确标记未完成。
7. **失败不伪装完整**：覆盖记录不存在、超范围、损坏、超时和模型上下文超限，确保界面状态与实际注入范围一致。
8. **质量检查**：用固定命盘和问题对比修改前后的回答，人工核对事实一致性、条件完整性和引用准确性。文本增加或程序测试通过都不等于答案已经更准确；评测不自动修改全文注入规则。

## 9. 实施顺序

先实现全文转换与单盘/合盘注入，并用源正文相等测试锁定行为；再同步请求容量、输出配置、提示词和界面反馈；随后运行相关 TypeScript、Rust、流式及端到端验证，检查四个平台共用逻辑；最后更新说明并通过现有构建流程验证安装产物。

已按“源正文完整传入、程序不再替模型选择档案段落”实施业务代码。合盘已完成的问答也按原顺序带入后续问题。真实样本逐专题字符串比较、长请求、容量、可选输出设置和流式结束状态均设有自动回归。

## 10. 实施验证记录

- 十组真实教学盘的 13 专题逐项与源记录相等；同盘切换问题和选择不改变档案正文；缺失专题不冒充完整。
- Rust 本地模拟服务验证两种协议、超过旧 256 KiB 的真实记录及长历史、输出参数省略或按配置传递、配置重启持久化、容量拒绝不发送残缺请求、取消和超时。
- TypeScript、档案回归、AI 上下文/流式回归、模型配置、共享回归及依赖边界检查通过。`dataset:tools -- evaluate` 也通过十组教学盘的全文检查。
- Rust 测试 16 项通过；浏览器针对性检查 20 项通过、18 项按平台分工跳过。Web 的真实 HTTP 上游与原生适配器 IPC 均验证 Chat Completions / Responses 下的单盘、学习、合盘全文及超过 256 KiB 的请求；Rust 另验证实际 HTTP 转发。上游使用本地模拟服务，未调用付费模型。
- `build:web`、`build:app` 和 macOS `build:desktop -- --ci --bundles app` 通过。Web 独立包与 macOS `.app` 内全部 77 年压缩资料通过 SHA-256 / 字节数校验；macOS 应用通过本地 ad-hoc 资源签名校验。未在本轮生成 Android、iOS、Windows 安装产物。
- 未调用真实模型进行回答质量对比，验收第 8 项仍需人工评估。全文增加和自动测试通过不能据此宣称推理准确率已提高。
